# 2026-10-22 arm_gesture 现场故障与修复边界

现场使用镜像 `release.261022.4fb8812` 执行左臂 wave，操作员观察到快速抬手、动作失败及黄灯，随后手动关机重启。该旧镜像不应继续用于动作验收。此次排查仅通过只读日志、固件配置和状态查询进行，没有复现动作、清错、修改电机参数或部署修复。

## 已取得的直接证据（Asia/Shanghai，UTC+08:00）

- 19:19:57.274，厂商 `pnd_service_dds` 日志记录 `Joint [17] ... error code: 64`。
- 同时发生 `PublisherStateMachine transition: WORK -> DAMPING`、`has_actuator_error=1`、`LightController Error added: ACTUATOR`，与现场卡住、黄灯一致。
- 报错前，17 号关节等多处的增益在两组参数间反复切换，例如 `Kp:6 -> 37.5 -> 6`、`Kd:0.816108 -> 0.163222 -> 0.816108`。其他关节也同步来回切换，表明低层收到竞争的控制流。原来仅在 Bundle 内阻止卡片相互调用，不能阻止已经运行的厂商 RL 控制器继续发包。
- 实际安装的 `configs/device/joints_info.json` 明确：17 是 `shoulderPitch_Left`，其位置范围为 `[-1.047, 2.042]` rad。原 wave 的 −85° 目标超出下限。固件限位的匿名快照作为离线测试数据保存，未包含设备地址或标定偏置。
- 实际服务的整个 Pro 关节顺序与主线一致。旧 SDK 全身例程的不同编号表不适用于直接替换这台机的编号。
- 19:21:59 开始系统正常关机，操作员确认是手动重启，不是已证实的程序导致自动重启。

## 修复

1. wave / salute / reset 必须显式传入布尔 confirm=true，并在 schema 中标记危险动作；缺失或非 true 在启动控制器和手型联动前拒绝，stop / info 无需确认。目标接受前只读查询控制域，RL、未知或查询失败均返回 `CONTROL_CONFLICT`，不发 LowCmd，也不联动手型。程序不自动切换控制模式。传统域是必要条件，操作员仍需按厂商要求确认开发者模式及无其他低层写入者，不能把“有反馈”视为控制权证明。
2. 活动期间由独立线程定期进行有界控制域查询；控制域变化、错误或控制权检查过期，立即停止本驱动低层发布，不向新的控制者发送释放增益包。
3. 保留真机服务对应的关节顺序与主线增益，把命令范围收进本次实际固件包络；wave / salute 的肩前摆目标改为 −45°。原 −85° 及其他超限目标在下发前拒绝。
4. 首次接管时使用持续更新的最新实测全身姿态，避免把启动数分钟前的快照突然写回。reset 返回本次接管姿态。
5. 最终发布路径逐帧限制角度增量，即使调度延迟也不能按墙钟时间跳到轨迹终点；重新设定目标从最后已写指令起步。
6. 反馈故障日志包含具体关节、索引及厂商状态码；动作终态记录 action_id / status，便于将下一次报告与 ACP 对齐。

## 尚不能下的结论

错误码 64 的精确硬件含义、是否有机械阻挡、实际跟随速度/电流，以及排除控制冲突后的电机状态仍需厂商或操作员确认。后续关机阶段还出现 encoder error 文本，不能据此反推 64 就是编码器故障，也不能宣称故障已由软件完全排除。

原驱动未保留逐帧实际/目标历史，无法从这次日志证明第一帧跳变或调度追赶已经发生；这两项是已通过代码与离线测试确认并补齐的保护缺陷。离线通过、bot 审查及镜像成功构建均不等于硬件已安全验收。修复版未自动部署、未进行真机动作验证。

# S10 stationary-feedback and sit_down release — 2026-10-30

Branch: `feat/s10-stationary-sit-down-20261030`, targeting upstream `main`.
This version carries PR #467 at `afb1f426` (including the earlier PR #451
implementation) and integrates the latest upstream main. It is a replacement
review candidate; PRs #451 and #467 are not closed or changed by this update.

The public downward action is now `sit_down`, consistent with `stand_up`.
Both `sitdown` and `stand_down` remain dispatch/completion aliases for saved
workflows, and returned action names use `sit_down`. No posture semantics change.

## Changes since PR #451

- Accept the exact legacy Core `{ok: true, action_id}` receipt as endpoint
  acceptance so a successful callback is not retried. This does not claim that
  the legacy endpoint caches or deduplicates callbacks after a lost response.
  Modern receipts still require a valid matching action ID and receipt state.
- Expose `sit_down` while retaining `sitdown` and `stand_down` for saved canvases. The operation
  continues to use the existing lie-down controller and feedback requirements.
- Return concise locomotion status, results and ACP payloads. Preserve protocol
  identifiers and failure fields; retain full evidence through `info` and the
  durable task store. Accepted commands explicitly tell callers to wait for ACP.
- Log repeated automatic Prepare blockers only when the meaningful outcome
  changes; preserve preparation, authorization and stopping behavior.
- Verify the historical G1 reference against its recorded Git tree and hashes,
  allowing current upstream G1 files to evolve without reverting them.

## Site follow-up — automatic preparation

On 2026-10-30 (Asia/Shanghai), the official ARM64 image
`release.261030.afb1f42`, bound to commit `afb1f426`, was deployed as a replacement
Driver while retaining previous containers/images. Its 70 runtime payload files
matched the reviewed source. Core identity, image, configuration and start time
remained unchanged; the canvas layout was preserved.

The replacement inherited `S10_AUTO_PREPARE=0` from the preceding container,
although the existing machine-bound version-2 policy explicitly permitted
automatic startup and renewal. The supervisor therefore did not start. The
locomotion card could be running with fresh feedback while reporting
`operator_session_unavailable` and `command_channel_not_prepared`.

The site repair recreated only the Driver with `S10_AUTO_PREPARE=1` and persisted
that value in its Compose service. It preserved the existing policy, permission
scopes, mounts, limits, state and previous containers. The final readback showed:

- Automatic Prepare: `session_active`.
- Operator session: authorized.
- Command publisher: prepared, two matched subscribers, channel ready.
- Locomotion readiness and `stand_up` readiness: true; blockers: empty.
- Active motion task: none; container restarts: zero.
- Core unchanged; no posture or velocity command issued.

This follow-up makes the service switch explicit and adds a deployment-to-runtime
regression for approved, denied, legacy and deliberate opt-out policy cases.
It does not alter Driver control code, Core, policy validation or motion guards.
The running robot remains on the verified `afb1f42` image; evidence above is for
that image with the repaired site configuration, not a future rebuilt image.

## Follow-up: bounded stationary corroboration

After the readiness repair, a 1 m/s backward task sent zero frames but failed
the old 1.2-second stop confirmation window. A subsequent read-only check found
persistent raw velocity around -0.157 m/s while odometry remained near rest.
The operator confirmed physical rest; this finding is distinct from the earlier
disabled-supervisor configuration issue.

The candidate adds a bounded motion/odometry stationary exception and a 2-second
stop budget within the original total deadline. See [stop diagnostics](STOP_DIAGNOSTICS.md)
for exact criteria and comparison with G1 and M20. It keeps the raw evidence,
task outcomes, authorization, e-stop and fault protections; it never replays the
failed task or changes its recorded result to success. This section describes
the candidate source; deployment evidence must identify the later image or
runtime explicitly rather than attributing it to `afb1f42`.

The stationary-feedback candidate passed the selected release gate with 706
tests passed and 1 skipped in 64.11 seconds before the final action rename.
It was built on the robot from the verified ARM64 `afb1f42` base as the local
image `stationary-odom-0866221c6616`; all 70 runtime payload hashes were verified.
Readback showed authorization and command channel ready, `stand_up` ready,
empty blockers, `failed_closed: false`, no active task and unchanged Core.
Previous containers and task history were retained; no physical action was
issued for this validation. This local image still uses the earlier `sitdown`
name. The final `sit_down` source rename is covered by the PR regression run;
it has not been substituted into the running robot image by this commit.

## Follow-up: remove persistent software latches

The candidate no longer requires a manual unlock after an ordinary command
failure or a transient Prepare exception. The bounded supervisor retries current
readiness and reconstructs a closed worker under a still-valid session without
renewing it. Explicit `stand_up` also uses current checks to rebuild the channel.
An explicit card stop/disable, active task, current fault, e-stop or invalid
authority is still respected. Monitor publication errors are diagnostic-only.
Task-storage integrity, request deduplication, finite execution/zero commands and
total deadlines remain intact. `sit_down` has no special unlock-only meaning.

An unconsumed `/IMU_DATA` capture was removed from the offline fixture. Consumed
samples and provenance remain; no hardware state or task history is removed.

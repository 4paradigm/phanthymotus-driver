## 接入前的必要能力

1. 三个经过验证的脚部动作，以及可返回的中立站姿。现有 loco / loco_servo 是整机速度控制，不能作为脚宽或单脚落点接口使用。action_recording 是否能得到需要的腿部动作尚未验证。
2. 提供上述动作的可复用基础 Card。建议通用姿态名为 feet_together、feet_apart、feet_staggered、neutral；游戏的石头/布/剪刀映射留在 Skill 层。仅有 Card 名称或 Schema 不代表已具备运动能力。
3. EDU 的 LowController 可用于运动开发，但还需要自己的平衡和运动策略。必须先在仿真与受控实机验证动作过渡、结束状态和停止行为，不能从一组猜测关节角直接开始对局。
4. 口头启动与报招需要接通 Bumi mic、回声消除、ASR 和决策核心。核查时 ASR 与回声消除均 idle，当前画布只有 remote_message 作为对话输入；文本框消息不等于机器人已经能听懂语音。

## 场景 Skill 的执行设计

用户说“开始石头剪刀布” → 加载 Skill → 检查经过验证的动作能力与语音链路 → 暂停会同时触发挥手的迎宾流程 → 随机预选本轮出招 → 语音倒数 → 仅在报招窗口接收玩家出招 → 执行对应脚部动作并等待真实状态确认 → 播报胜负 → 回到已验证的中立姿态 → 等待“再来一局”。

机器人自己说规则、倒数和播报结果时不把 ASR 回声当成玩家报招。收到“停止游戏”、输入超时、动作结果不确定或保护状态时结束当前流程，不继续出招或猜测动作完成。

下一阶段需要先核实原厂腿部示教与稳定回放能力，再验证动作；卡片边界见 [FOOT_POSE.md](../../FOOT_POSE.md)。本目录未提供可安装的 `skill.json`，规则测试通过不代表真机游戏完成。

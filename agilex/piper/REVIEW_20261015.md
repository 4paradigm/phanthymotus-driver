# PiPER ARM64 two-card review candidate — 2026-10-15

## Current interface

The default canvas has **Arm control** and independent read-only **Joints**.
Arm control provides relative Cartesian Move, absolute/relative six-joint arrays,
fixed Reset, Set gripper, Stop and Get status. Joints owns the 10 Hz measured
radian skeleton topic; optional live camera stays in the background. The new
bundle neither declares nor publishes `/state/parameters`. Status, faults,
effective limits and task results remain available through Get status. Legacy
monitor bundles retain their parameter-output default for compatibility.

Uncalibrated Move translates along SDK end-frame axes, preserving measured
orientation. Arrays accept strict JSON text or native arrays; absolute arrays
allow null to keep a fresh measured component. Relative arrays reject null;
zero relative requests issue no preparation or control commands. Default speed
is 1%, range 1–10%, and Move magnitude is limited to 10 mm. Pose/rotation remain
hidden and rejected without verified TCP calibration. Candidate MOVE_P remains
closed until the exact device/firmware/driver/configuration has recorded physical
acceptance; it has no automatic fallback, fault reset or retry.

Reset now uses the official SDK go-zero example's six joint angles
`[0,0,0,0,0,0]` degrees, default speed 1%. It does not read the legacy saved pose
or configured preset; those files/helpers are preserved. Set position is removed
and rejected. Guarded stationary teaching exit and measured hold still precede
nonzero control requests. Reset retains limits, cancellation and stable-arrival
checks, leaves the gripper unchanged, and never invokes ResetPiper, calibrates
zeros, clears faults or disables motors. Its physical return path is pending
operator acceptance, not claimed safe by simulated tests.

The only public gripper action is `set_gripper_opening` (**Set gripper**),
`width_mm` 0–70 mm, default 20 mm (narrowed by effective deployment/SDK limits).
Old open/close requests fail with a refresh-interface message.

## Asynchronous completion

Each accepted asynchronous action has its own action ID, terminal outcome and
bounded delivery record. Completion delivery verifies the HTTP `ok` and matching
action ID, uses four attempts with bounded backoff, and never retries robot
commands. Delivery occurs outside the motion lock; delayed callbacks cannot
replace a newer action's result. Fast synchronous completion returns its actual
result without manufacturing a running task. Get status exposes delivery
attempts/results. Success, error and cancellation are all terminal outcomes.

The separate Core fix passes the real model device ID through both detail-entry
paths and caches early ACP results until actual task registration, with bounded
deduplication. Driver retries alone cannot fix older Core dropping early results.
The two-card driver and that Core fix were deployed together as local ARM64 test
images after the operator stopped intelligent control. No movement, mode,
enable, disable, teaching-exit or Reset was invoked by deployment checks.

# 天轶遥操执行链适配与审查计划

## 目标与范围

本文件保留 v1 执行链及先前审查证据。当前已授权的后续实现以 [三段末端架构计划](teleop-end-effector-architecture.md) 为准：PICO 接入与相对映射保留在普通 ActuCore，天轶 IK、碰撞、可视化、模型与显式收臂迁入 Driver 的 motion_control，再进入同仓 arm。旧 v1 与历史测试结论不改写为新架构真机通过。

来源开发树基于 b1cbc93e3b1e15f67920cd4e4218110e2749de3b。本审查树从实时主线 19729470df853926ba170838a1e158c17ae1392e 移植 23 个显式路径，无冲突，保留主线新增的导航停止修复。变更限定 Tianyi bundle 入口、原异步动作取消语义、连续执行器、构建、相关测试和文档，不改其他机型或 Agent Core。

## 已实现

- 默认关闭的 teleop_executor，回环 MCP 管理与本机 domain-42 连续目标，厂商 domain-0 输出复用现有 ArmPlugin/HandPlugin。
- 共享执行权覆盖旧动作、轨迹、手势、手部、头腰、底盘、导航和 servo；取消超时继续保留忙状态，不静默抢占。
- 50 Hz 最新目标、签名/会话/序号/原始时效验证、限位限速和有限领先；旧会话报文不干扰新会话。
- 后续新鲜反馈确认保持和释放；短暂时效缺口及 IK recoverable_hold 同会话恢复，显式暂停/真正故障采用完整恢复。
- 幂等管理请求与取消，防止成功回复丢失后 lease 旋转或迟到请求意外接管。
- 独立安全反馈调度、有界让出、每次准备采集固定体位基准；双臂-only 不要求手部输出或手部反馈，却仍报告其状态。
- 首次限时验收与显式持续操作两种准备方式；准备不等于获取执行权，不伪填普通验收记录。
- 有界内存四段追踪与厂商发布诊断；不把发布成功等同于实际到位。
- 构建编译实际消息依赖并校验入口导入，默认功能保持关闭。

## 架构后续事项

1. 当前 motion-target 协议与仓库已有 motus.control/1 ControlSink 并存。此轮先保留已验证行为和生产边界；后续独立评审哪些时效、仲裁、诊断语义可复用，避免直接替换造成停止/恢复回归。
2. 旧动作插件与遥操共享同一 Driver Python 进程，反馈调度通过专用执行器和有界让出缓解。需持续观察实际负载；不把一次低延迟样本当成确定性实时保证。
3. 停止确认采用订阅到达时间；厂商消息到达与硬件采样新鲜度不能混同。Driver 崩溃后的有限剩余目标需独立物理验收。
4. 持续操作准备、短时首次验收和普通 Live 验收是三种不同依据，后续应在卡片中清楚展示，避免现场临时模式长期隐式化。
5. 旧 v1 收臂由 ActuCore 插值；新 v2 保留显式操作者/项目结束语义，轨迹计算和停止确认移入 Driver。断线/暂停仍不自行回零。

## 2026-09-22：bot 构建、日志及协议审查修复

PR #321 在 `6b6d767` 的 ARM64 构建失败于 `main.py → ext_devices.py → audio_msgs` 导入。第一轮把专用脚本额外注入的消息源纳入标准上下文，离线 26 项通过，`2255037` bot 构建也成功（10 分 04 秒）。但这只消除了症状：“上下文缺包”不是完整根因。

随后只读 registry manifest/config，确认 `2255037` 前 15 层与基础镜像 `82d45949…649f` 完全一致，基底早已编译 audio_msgs 并由 ENTRYPOINT 加载 `/ros_ws/install`。Docker RUN 不执行该 ENTRYPOINT，旧导入检查漏加载此 overlay。最终修复撤销额外消息源、COPY 和重复 audio_msgs 编译，两个入口只准备 Tianyi/common；编译、导入和运行明确按 ROS → 基底 audio → Tianyi 顺序加载。缺 overlay 或真实消息导入失败仍阻断，不再忽略 setup 失败。标准 build.sh 保持不变。

镜像体积按 registry 压缩层实测：`2255037` 为 341,727,193 B，基础层为 261,578,370 B；冗余 audio_msgs 源 COPY 独立层 743 B，三包共同编译层 6,754,542 B，不能把后者全部归因于 audio_msgs。当前移除冗余，新镜像净差待最新构建 manifest 确认；不声称零增量，也不拿不同 Dockerfile 的总量差充当包增量。

同一 HEAD 的 bot 指出 DDS `--bus` 子进程未安装安全日志。现于子入口最前面复用 `common.logsafe.install(check_fd=False)`，在 ROS 导入与配置检查之前保护 Python stdout/stderr。镜像直接导入已 COPY 的 common；源码仅按 main.py 的仓根布局解析，不增加任意环境路径入口。原生库直接写 fd 不在 logsafe 范围内。

验证：真实启动源码/镜像布局的子进程，使用 ROS stub 与匿名 socketpair 验证 stdout/stderr 原子写入、控制字符清理、导入异常；原 `2255037` 隔离副本能复现未安装保护。两个构建入口及 Dockerfile 编译/导入/运行 Shell 的加载顺序、缺 overlay 失败均在临时目录实际运行。上述测试加 MotionGate、管理/续接/恢复、生命周期、元数据、通用 ControlSink 与全仓 Dockerfile 源路径检查共 **181 项通过**（4.14 秒）；bash 语法和 diff 检查通过。实际修复后镜像与 bot 最新审查仍待提交后验证，本轮未访问机器人。

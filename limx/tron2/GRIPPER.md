# TRON2 夹爪卡片

在 Motus 的 TRON2 工具库中，将 `gripper` 拖到画布。驱动上线后可使用以下操作。新卡片默认选择 `get_state`，读取状态不会移动夹爪。

| 操作 | 用途 | 需要填写 |
|---|---|---|
| `get_state` | 读取左右夹爪状态 | 无 |
| `open` | 张开所选夹爪至最大开口 | side、speed、force |
| `close` | 闭合所选夹爪至最小开口 | side、speed、force |
| `set_opening` | 调整所选夹爪的开口度 | side、opening、speed、force |
| `recover` | 确认停止后恢复失败任务，不发动作 | 原任务的side、confirm_stopped=true |

`side` 选择 `left`（左夹爪）或 `right`（右夹爪）。一次操作只改变所选夹爪，不向另一侧发送指令。

`opening` 为0至100的相对开口度：0是最小闭合，100是最大张开。`speed` 为大于0至100的速度档位；`force` 为0至100的夹持力档位。这些值不是毫米、毫米/秒或牛顿。速度和夹持力均须明确填写，卡片不会自行选择适合物体的档位。

执行开合前，确认机器人连接正常并处于上层开发模式。卡片不切换机器人模式，也不驱动机械臂、头部或另一侧夹爪。读取状态不要求执行开合。

动作响应包含跟踪编号。仅在厂家接受指令，并且之后连续多次状态查询报告所选侧达到目标开口度时，才报告目标确认。开口度相差不超过1个相对档位、至少3次新响应且持续至少0.5秒才视为稳定；厂家反馈时间戳必须比动作前及上次反馈更新，重复的缓存状态不能确认到位。缺少反馈时间戳时拒绝发送开合指令。确认基于厂家状态报告，不是额外位置传感器的校准测量。

**目标开口确认不代表已经夹住物体。** 卡片不判断物体是否存在、接触力或抓取是否可靠。夹持物体时，物体可能阻止夹爪达到最小开口；此时卡片会提示未确认目标，不报告抓取成功。可先读取状态，再结合实际物体选择合适的目标开口及档位。

回执丢失、反馈异常或目标未在20秒内确认时，卡片不会自动重发开合指令。上一动作结果不明时，驱动拒绝新增开合。先现场确认夹爪已停止、空载且手和障碍物已离开，然后选择原任务的侧，使用 `recover` 并勾选 `confirm_stopped`。恢复会检查连续更新、开口稳定且双侧速度为零的反馈，并确认原任务结果已通知平台；不满足条件时保持锁定。恢复不重发开合，不把原来的失败改成成功。系统 `stop`、恢复和关闭驱动都不是硬件急停，不承诺停止已经发出的运动。

状态查询同时显示任务锁、具体失败原因和 `can_accept_motion`，查询成功不代表原任务已恢复。现场曾出现 `open` 目标100而反馈稳定94，仍按未到位处理，确认停止后才能恢复；不要据此扩大到位容差或提高力档位。需要较小开口时使用明确的 `set_opening` 目标。

骨架上的闭合夹爪轮廓仍是固定示意，与这张卡片查询的开口度分别显示；本次没有添加未经校准的开合动画。

## 实现与验证

遵循本仓库 `README_dev.md` 的 MCP工具、`x-action-params`、生命周期和 ACP 规范，参考 `brainco/revo2/device.py` 的左右手/动作分组形式，以及 `realman/rm75_6f_v/pick_place/gripper.py` 的故障检查和反馈确认思路。没有复用其他型号的硬件协议。

厂家协议依据：[TRON 2 SDK开发指南，逐际二指夹爪章节](https://www.limxdynamics.com/zh/documents/847884267345285120)。状态查询使用 `request_get_limx_2fclaw_state`，开合使用 `request_set_limx_2fclaw_cmd`。每次请求校验guid、accid及响应类型，只发送所选侧的opening/speed/force三项。请求通过现有机器人WebSocket连接收发，保留已有唯一接收循环；回调复用现有受验证的Core HTTPS连接。

夹爪与本驱动的机械臂动作共用 `arm_l`、`arm_r` 完成通道，并在驱动内部双向检查动作所有者。机械臂运动或结果不明时不发送夹爪指令，夹爪运动或结果不明时不发送机械臂指令；此声明不提供跨驱动或跨进程的硬件锁。当前版本没有加入遥操作集成。

本地测试使用假机器人与真实回环 HTTP/WebSocket，不连接真机。真机固件支持情况、速度/力档位效果和夹爪反馈语义仍需现场验证；源码完成不代表已部署。
